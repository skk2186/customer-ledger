# Excel 契约（阶段三）

## 导出范围

系统只导出 `.xlsx`，不导出 `.xls`。提供当前客户、客户汇总总表和全部客户账目三种导出；全部账目工作簿的第一个 Sheet 必须是 `客户汇总总表`，后续客户 Sheet 按稳定的客户名称升序排列。

客户 Sheet 名必须与 `Customer.name` 完全一致。名称去除首尾空白后为 1–31 个字符，不含 `: \ / ? * [ ]`、控制字符或首尾单引号；不截断、不自动改名。遇到不合规名称时导出失败并提示处理。

## 客户 Sheet

第 1 行合并 A:M 并写入客户名称，第 2 行必须是以下 13 列，顺序不可变：

`日期、总货款、运费、卸车费、退板吨位、退板金额、问题扣费、平方数、应收款、实收款、欠款、抹零、付款方式`

每一条有效 Shipment 生成一行。应收款、分配实收、欠款必须使用 `calculation_service.py` 的统一计算结果，保留带符号的负值。付款方式只用于展示，数据库中的付款方式和说明仍分开保存。

有效 Payment 的未分配余款大于 0 时，追加一条预收行：日期为付款日期，非收款金额/数量列为 0，应收款为 0，实收款为未分配余款，欠款为负的未分配余款，抹零为 0；付款方式以“预收款”开头，并包含付款方式和简短说明。这样客户 Sheet 的收款页脚等于有效 Payment 总额，且等于发货分配实收与预收行之和。

最后一行 A 列为 `合计`。发货与预收行的数字列在页脚求和；日期列使用 Excel 日期类型，金额和数量使用 Excel 数字类型，金额由整数分以受控 Decimal 转换为元，禁止二进制浮点计算结果直接作为业务真值。工作簿不得包含公式、外部链接、宏、VBA、Power Query 或网络资源。

## 客户汇总总表

Sheet 名固定为 `客户汇总总表`，列顺序固定为：

`客户名称、总货款、运费、卸车费、退板吨位、退板金额、问题扣费、平方数、应收款、实收款、欠款、抹零`

每个客户一行，最后一行为 `合计`。实收款使用有效 Payment 总额；欠款使用客户净余额，保留负值语义。汇总仍按有效 Shipment、Payment 和抹零计算，不改为只减 PaymentAllocation。

## 旧 `.xls` 迁移

`.xls` 只由 `xlrd` 只读解析，禁止用 `openpyxl` 读取。解析流程为 Parse → Normalize → Dry Run → Mapping/Exceptions → User Confirmation → SQLite Backup → 单事务导入 → Reconciliation。

- 正式业务区固定为 A:M：日期、总货款、运费、卸车费、退板吨位、退板金额、问题扣费、平方数、旧应收、旧实收、旧欠款、抹零、付款信息；N 列及以后不进入正式模型，只生成异常提示。
- 必须区分标题、表头、日期业务行、空行、合计行、备注/预收行和未识别行；扫描不会因遇到第一条合计而停止。
- 客户身份来自工作表名和标题。冲突、无法识别或多个候选不会静默合并，必须进入待确认映射。
- 当前 Shipment 的应收由现行计算服务重算；旧应收和旧欠款只用于对账异常。付款金额和付款信息都清楚时才建立 Payment；不清楚的记录只进入异常。
- 预收、从预付款冲减等文字只产生待确认候选，未经确认不得写入 Payment 或 Allocation。厂里零售统一映射为 `厂里零售`，仍使用普通 Customer、Shipment、Payment、Allocation。
- 历史汇总 `.xls` 只作聚合核对参考，不作为导入源。Dry Run 不写 Customer、Shipment、Payment、Allocation 或正式 ImportRecord，只写被忽略目录中的匿名聚合报告。
- ImportRecord 来源身份至少由源文件 SHA-256、Sheet 和原始行号组成。同一源重复执行不产生新记录；文件哈希变化时不得按日期和金额去重。
- 确认导入前必须成功完成 SQLite Online Backup；备份失败阻止导入。导入使用单事务，任一异常全部回滚，完成后重新按现行规则对账。

真实旧表只允许位于被忽略的 `private_samples/` 或用户明确指定的外部目录，不得进入 Git、测试代码或阶段报告；阶段报告只写聚合数量、哈希和异常类别，不写客户名称、金额或备注。
