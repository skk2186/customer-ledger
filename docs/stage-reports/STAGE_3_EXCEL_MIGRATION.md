## 阶段三确认导入安全修复

### 修复原因

旧账确认导入在“实收金额大于 0、付款方式为空”时，原先可能先写入发货，再以异常状态记录导入结果。这样既没有建立完整收款，也会让同一来源行被幂等记录跳过，后续无法补充付款方式。预收候选的确认也需要在日期、金额和付款方式齐全后才允许落正式账务。

### 修复内容

- 确认导入在备份和任何业务写入前，统一校验所有有实收的业务行；付款方式必须来自旧表自动识别结果或完全匹配的来源行确认选择。缺失、非法或“标记未付款但存在实收”的行直接阻塞，不创建 Customer、Shipment、Payment、PaymentAllocation 或 ImportRecord。
- 移除“先写发货、再写付款方式异常 ImportRecord”的路径。付款方式确认成功后保存完整 Payment，并按现行计算规则分配，超额部分继续作为未分配预收；客户净余额公式未改变。
- 迁移页按 `源文件哈希:工作表:原始行号` 展示待确认行，提供固定的五种付款方式下拉选项，显示异常类型及数量和对账提示；路由按稳定来源键传递用户选择。
- 勾选导入预收时，预收候选必须同时具备有效日期、大于 0 的金额和明确付款方式；否则保持未落库并阻塞本次确认。未勾选时仍可保留为待确认候选。
- 保持“暂未付款”快捷语义：创建发货但不创建 0 元 Payment，也不保存虚假的付款方式；阶段三页面继续保持全中文。
